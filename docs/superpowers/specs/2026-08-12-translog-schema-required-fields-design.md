# TransLogV1 Required Fields from Schema File — Design

## Overview

The user authored `packages/server/config/translog_required_fields_schema.json`, a richer, business-authored definition of which fields must be present in a `transLogV1` Kafka message, broken down by the message's own `status` value (`common_fields` always required, plus per-status additions in `schemas_by_status`). Today, `transLogV1`'s required-fields check (`KAFKA_TOPIC_DEFINITIONS.transLogV1.requiredFields` in `kafka-check-definitions.ts`) is a single hardcoded, status-agnostic list of 23 fields. This replaces that hardcoded list with one driven by the new schema file.

**Scope, explicitly narrowed during brainstorming:** the schema file also describes `conditional_fields`, `must_be_absent_or_empty`, `known_optional_fields`, and an "unexpected fields" detection concept in its own `_meta.how_to_use` notes. None of that ships in this increment — only required-fields presence checking, matching exactly what the app already does today for every topic, just with richer, status-aware data for `transLogV1`.

**Known schema-data issue, confirmed during brainstorming:** the file's `schemas_by_status.PROCESSING` block uses snake_case, nested-path field names (`order_no`, `dest_asset.dest_asset_type`, `payment.payment_no`, …) that don't match any real `transLogV1` message seen so far (every real message pasted in this project uses camelCase: `transID`, `appTransID`, etc.) — it appears to describe a different message/proto entirely. The `SUCCESS` block, by contrast, is camelCase and matches real messages. The user will fix or remove the `PROCESSING` block themselves; the code is written to be fully data-driven (whatever `schemas_by_status` contains is what gets checked), so no code change is needed once that's corrected. Until then, real `PROCESSING`-status messages will show false "missing fields" against the current (wrong) `PROCESSING` block — an accepted, temporary risk, not something this increment works around in code.

## Architecture

- `translog_required_fields_schema.json` is committed to the repo (not gitignored) — it's business-rule data, not an environment-specific secret, same category as the hardcoded field lists already committed in `kafka-check-definitions.ts`.
- New module `packages/server/src/translog-required-fields.ts` exports `getTransLogRequiredFields(status: string | undefined): string[]`. It loads and parses the JSON file once, synchronously, at module load (same file-path-resolution style already used for `kafka.yaml`), and returns the deduplicated union of `common_fields.required_fields` with `schemas_by_status[status]?.required_fields` (an empty array if `status` doesn't match any key — i.e., falls back to just the common fields). If the file is missing or fails to parse, this throws immediately at load time rather than silently degrading — it's a checked-in file expected to always exist, unlike the optional, environment-specific `kafka.yaml`.
- `kafka-check-logic.ts`'s `checkRequiredFields(message, topic)` gains one topic-specific branch: when `topic === 'transLogV1'`, it calls `getTransLogRequiredFields(payload.status as string | undefined)` (reading `status` off the same payload it already has) instead of `KAFKA_TOPIC_DEFINITIONS.transLogV1.requiredFields`. `refundLog` and `paymentAuth` are entirely unaffected — they keep using their existing static `requiredFields` lists.
- The old hardcoded 23-field `requiredFields` array for `transLogV1` in `kafka-check-definitions.ts` is removed (fully replaced, not left as unused dead code). `correlatorFields`/`hasDataWrapper` for `transLogV1` are untouched.

## Testing

- New test file (or a new `describe` block) verifying `getTransLogRequiredFields`: returns `common_fields.required_fields` alone when `status` doesn't match any `schemas_by_status` key; returns the union (deduplicated) when `status` does match (e.g. `'SUCCESS'`); the returned list has no duplicate entries even where a status-specific field also appears in `common_fields`.
- `kafka-check-logic.test.ts`'s `checkRequiredFields` tests for `transLogV1` are updated to reflect the new, larger, schema-driven field list (the existing `toHaveLength(23)` assertion changes to reflect the real `common_fields` count) and gain a case proving a `SUCCESS`-status message is checked against the union while some other/missing status is checked against `common_fields` alone.
- `refundLog`/`paymentAuth` tests are unaffected — included in the plan only as an explicit regression check, not because their behavior changes.
